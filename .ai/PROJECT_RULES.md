# Aura v5 — обязательные правила для ИИ

Эти ограничения относятся к пользовательским фото товаров и профилей поставщиков. Не меняйте их без прямого согласования с владельцем приложения.

## Фото товаров и поставщиков

- Максимальный размер каждого нового загружаемого фото — **50 КиБ (51 200 байт)**.
- Формат объектов в Supabase Storage — только **WebP (`image/webp`)**. Исходные JPEG, PNG, HEIC и другие входные форматы нужно преобразовать до загрузки.
- Обязательно принимать распространённые фотоформаты с телефонов: JPG/JPEG, PNG, WebP, AVIF и HEIC/HEIF. HEIC/HEIF декодировать через `heic2any`, если браузер не умеет открыть файл напрямую; пустой или общий MIME-тип мобильного файла сам по себе не повод его отбрасывать.
- После преобразования WebP должен оставаться видимым через обычный `<img>` во всех поддерживаемых версиях iOS/Android. Если декодирование невозможно, показать понятную ошибку, а не сохранять URL пустого/битого файла.
- Общий клиентский конвейер — `lib/image-policy.ts` и `lib/image.ts`. Не добавляйте второй компрессор или путь, который загружает исходный файл напрямую.
- Перед отправкой нужно проверять одновременно MIME-тип и точный размер в байтах. Если лимит не достигнут, загрузку отклонить с понятным сообщением; нельзя молча отправлять файл больше 50 КиБ.
- Серверный предел задаётся в `supabase/migrations/011_product_image_limits.sql`: бакет `product-images`, 51 200 байт, разрешённый MIME `image/webp`. При изменении лимита синхронно обновить компрессор, UI-подсказки, миграцию, `supabase/schema.sql` и тесты.
- Потоки загрузки фото товара в `components/product-images.tsx` и `components/screens/sklad/add-edit-Product/product-images.tsx`, а также фото поставщика в `components/screens/suppliers/supplier-payout/supplier-card.tsx` должны использовать общий компрессор и записывать файл в папку активного магазина: Storage RLS сверяет первый сегмент пути с `current_shop_id()`.
- Не удалять и не переписывать существующие объекты автоматически. Новые ограничения не уменьшают уже загруженные файлы; преобразование или удаление старых фото требует отдельного подтверждения и плана.

## Что не менять этим правилом

- Не применять лимит пользовательских фото к логотипам, иконкам PWA/iOS, QR-кодам, этикеткам, скриншотам или другим генерируемым изображениям.
- Не менять структуру фото в товарах, права магазинов, Storage RLS, поведение камеры или офлайн-синхронизацию в рамках задачи о сжатии без отдельного запроса.
- После изменений в конвейере запускать `node --experimental-strip-types --test tests/image-policy.test.mjs` и полный набор `node --experimental-strip-types --test tests/*.test.mjs`.

1. Экономия токенов
Не читай весь репозиторий. Сначала rg -n / rg -l по ключевым словам, затем читай только нужные диапазоны строк.
Не перечитывай файлы, которые уже в контексте.
Независимые чтения и правки — параллельно, одним батчем.
Правь точечно (diff/patch), не переписывай файл целиком.
Не выводи в чат код, который уже записан в файл. Не пересказывай задачу.
Длинные логи — в файл, затем tail/grep.
Ответ: 1–3 предложения. Без вступлений, извинений и итоговых пересказов.
2. Качество кода (senior-уровень)
Чини причину, а не симптом. Найдя баг — проверь соседние места с тем же допущением.
Простота > хитрость. Без преждевременных абстракций; без мёртвого кода.
Строгая типизация: никаких any, @ts-ignore, as unknown as для обхода ошибок.
Обрабатывай ошибки и крайние случаи: пустые данные, офлайн, повторный клик, гонки.
Деньги и остатки — атомарно, в транзакциях; никогда не на клиенте.
Не добавляй зависимости без необходимости; сначала проверь, нет ли решения в проекте.
Имена — говорящие; комментарии объясняют «почему», а не «что».
